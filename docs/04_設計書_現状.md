# 進行管理エージェント 設計書（現状版・2026-09-20）

`01_実装仕様書.md` が「作る前の仕様」、`03_仕様からの差分.md` が「作りながら変えた判断」。本書は**いま動いているものの設計**を1枚で説明する。審査員・引き継ぎ・自分の3者向け。

---

## 1. 何をするシステムか

会社の中で「決まったこと」と「作られているもの」は別々の場所に散らばる。決定は議事録・チャット・メールに、成果物は Excel / Word / Wiki に。誰も両者を突き合わせないので、「先週据え置きと決めた数字が、今週の資料では変わっている」が起きる。

本システムは **5つの情報源を1つのグラフに正規化し、成果物が変わるたびに関連する決定を引き当てて食い違いを判定し、人に通知する** エージェント。人が指示しなくても、定期巡回とイベントトリガーで自分から動く。

```
 情報源                     正規化           統合グラフ                判断                行動
 ─────                     ────           ─────────             ────               ────
 会議（自作 Meet / fixtures） ─┐
 チャット（自作 Teams 相当）  ─┤  Event      events ─ links ─ tasks   抽出 → 紐付け →     通知（チャット/通知箱）
 メール（自作 Outlook 相当）  ─┼→ (1種類) →   ▲          ▲            矛盾検知 →          確認キュー
 Wiki（自作 Confluence 相当） ─┤            embeddings  findings      停滞/状態提案      状態更新の提案
 成果物（自作 SPO 相当）     ─┘                                                          会議室の準備
```

## 3. データモデル

### 3.1 中核（仕様書どおり）

- **events** — 全情報源を1種類に正規化した「出来事」。`kind` = utterance / decision / task_hint / artifact_change。`source`、`actor`、`occurred_at`、`ref`（出典の座標）、`quote`（原文）、`meta`（JSON）
- **tasks** — 決定から生成、または手動。`status`、`assignee`、`due_date`、`artifacts`（紐付く成果物）、`created_from`（生成元 event）、`priority`
- **links** — event ⇄ task の紐付け。`relation`（discusses / follows / changes）、`method`（explicit / context / assignee / embedding / llm / manual）、`confidence`
- **findings** — 検知結果。`kind`（contradiction / stalled / orphan_change / status_suggestion）、`evidence`（event id の配列・2件以上）、`confidence`、`severity`、`status`（notified / pending / acknowledged / dismissed）、`payload`（判定の内訳）
- **embeddings** — event/task の埋め込み（`llm_embeddings.npz` にも複製）
- **processed / sync_state** — 増分処理の進捗（stage × key）と、コネクタごとの最終取込時刻
- **cost_logs** — LLM 呼び出しごとの token と原価（キャッシュヒットも名目価格で記録し「全部 high なら」と比較できる）
- **agent_logs / settings** — エージェントの発話ログ、設定の上書き（閾値・在席・既読など）

### 3.2 自作ツール（UI のためのテーブル）

| 領域 | テーブル |
|---|---|
| チャット | chat_channels（channel/dm/group/team）, chat_messages（スレッド・編集・添付）, chat_reactions, chat_pins, chat_saved, chat_mutes |
| メール | mails, mail_state（フラグ/アーカイブ/ごみ箱/未読・ユーザー別）, mail_drafts |
| 予定表 | cal_events（kind・繰り返し series_id・出欠 rsvp・終日） |
| 会議室 | meetings, meeting_tracks（話者別録音 BLOB）, meeting_participants, meeting_notes（共有メモ）, meeting_chat, meeting_summaries |
| Wiki | wiki_pages, wiki_revisions（改訂ごとの本文・差分の元） |
| タスク付属 | task_checklist, task_watchers, task_activity |
| 横断 | tags（topic/team）, tag_links（message/task/artifact/meeting/channel/wiki） |

成果物本体は DB ではなく `fixtures/excel/`（ライブラリのルート）に `<名前>_vN.<拡張子>` として保存し、`versions.json` に更新者・日時・メモ・URL を持つ。

## 4. パイプライン（1回の巡回）

```
tick()
 ├ fetch    : 各コネクタ.fetch(since) → events に保存（増分）
 ├ extract  : 会議/チャット/メールの utterance → decision / task_hint      [LLM mid]
 │            ・引用検証: 抽出結果の quote が原文に存在しなければ破棄（幻覚対策）
 │            ・重複統合: 埋め込み類似 0.88（決定）/ 0.82（タスク）
 │            ・タスク自動生成は会議由来のみ。チャットは決定だけ拾う
 ├ embed    : 新しい event/task の埋め込み                                  [embed]
 ├ link     : 発言 → タスク（5段）
 │            ①explicit（語・成果物名・共有タグ） ②context（スレッド継承） ③assignee
 │            ④embedding（0.55） ⑤llm（[T1] 番号参照で id 非依存）        [LLM mid（⑤のみ）]
 ├ detect   : artifact_change ごとに
 │            ・候補: タスク直結の決定 ＋ 埋め込み上位（0.35）× 語彙ゲート（対象語を含む決定のみ）
 │            ・ガード: 時系列（決定が変更より前）、30日以内、数式セルの値変化は対象外
 │            ・判定: 決定・変更・関連発言・その後の決定を渡して判定        [LLM high]
 │              same_subject=false なら LLM が矛盾と言ってもコードで矛盾扱いしない
 │            ・decide_action: confidence ≥ 0.8 → 通知 / ≥ 0.5 → 確認キュー / それ未満 → 無視
 │            ・候補ゼロ → orphan_change（根拠のない変更）
 ├ stalled  : 7日以上動きのないタスク（会話・コメント・更新なし）
 ├ suggest  : 担当者の発言（「終わりました」「着手」「止まっている」）から状態更新を提案（LLM 不使用）
 └ calendar : 15分前に会議室を作りリマインド、議題案を投稿
```

**起動の仕方（ハイブリッド）**: 60秒ポーリングに加え、チャット投稿・メール送信・会議終了・成果物の保存（UI／監視フォルダ）・Wiki 更新で `agent.request_tick(reason)` が即時起動する。実測: アップロード → 約8秒で検知。

## 5. LLM の使い方（OrcaRouter）

| tier | モデル | 用途 | 割合 |
|---|---|---|---|
| high | anthropic/claude-opus-5 | 矛盾判定（1件ずつ、根拠と文脈を渡す） | $0.50 |
| mid | google/gemini-3.6-flash | 抽出・紐付け第5段・議事録要約 | $0.21 |
| embed | google/gemini-embedding-001 | 候補絞り込み・重複統合・紐付け第4段 | $0.001 |

- 全処理の実測 **$0.84**。全て high で回した場合 **$2.07**（削減 59%）。数字はダッシュボードとコスト画面に常時表示
- **マスキング**: 送信前に人名・メール・電話をプレースホルダ化し、応答を復元。引用検証はマスク後の文同士で行う
- **キャッシュ**: `fixtures/llm_cache.json`（chat）＋ `llm_embeddings.npz`（埋め込み・float16）。`replay` はキャッシュのみで動き API キー不要。プロンプトを変えたら `replay --record` で取り直す
- **料金表**は `/v1/models` から取得して `fixtures/llm_pricing.json` に保存

## 6. セキュリティ設計（やること / やらないこと）

| 項目 | 設計 |
|---|---|
| 送信データ | 判定に必要な最小限（決定・変更・関連発言）。個人情報はマスク |
| プロンプトインジェクション | 議事録は「ユーザーデータ」として囲い、指示として解釈しないと明記。fixture `2026-09-19_gogo_kensho.txt` に指示文を混入させた実演があり、抽出結果に漏れないことを議事録画面で表示 |
| 書き込み | エージェントは通知と提案までで、タスクの状態変更・成果物の書き換えは人が承認して初めて行う |
| 権限 | 各コネクタは読み取り専用スコープ（Graph なら Mail.Read / Calendars.Read）。書き込み API は呼ばない |
| 誤検知の抑制 | confidence の二段閾値、確認キュー、却下理由の保存 |
| 秘密情報 | `.env` のみ。リポジトリ・キャッシュに鍵は入らない |
| アップロード | 上限 50MB、`チャット添付/` と `.trash/` は git 管理外 |

## 10. 既知の制約

- 数式の書き換えだけ（値が同じ）は検知しない（評価の見逃し1）
- LLM のキャッシュはプロンプト文字列に依存。判定文言を変えると `replay --record` が必要（約 $0.3）
- 単一プロセス・SQLite。数十人規模までを想定
- 会議の映像は録画しない（音声のみ保存）。ブラウザ内蔵の STUN のみで、NAT 越えは環境依存
