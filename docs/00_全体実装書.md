# 決定と成果物の食い違いを検知するAIエージェント 実装書

2026-09-20

## プロダクト概要

### 解決する課題

会議で決めたことと、実際に作られている成果物が食い違う。これはリモート中心の組織で常態化しているが、誰も検知できない。議事録は Meet、議論はチャット、仕様は Wiki、数字は Excel と、情報が4つの場所に分断されているためだ。

人間がこの4つを突き合わせ続けるのは不可能で、実際には「気づいた人が指摘する」という偶然に頼っている。

### コア価値

**議事録の決定 → タスク → 進捗会話 → 成果物** を1本のグラフで繋ぎ、その上で矛盾を自律的に検知する。

一貫管理そのものは手段であって価値ではない。価値は次の一文が言えることにある。

> この資料の第3四半期の数字、3日前の定例で「据え置き」と決まった内容と食い違っています。

### デモの見せ場

**矛盾検知の一瞬に全てを賭ける。** ダッシュボードを見せて「情報が統合されています」で終わると、便利なツールという評価で止まり、自律性の点が伸びない。

見せる順序は以下で固定する。

1. 会議が終わる（議事録が自動で取り込まれる）
2. 数日後、誰かが Excel を更新する
3. **エージェントが自分で気づき、根拠3点を添えて指摘する**
4. 人間は確認して承認するだけ

3 が主役。ここまで一度も人間が指示を出していないことを明示する。

### AI HACK テーマとの対応

テーマは「業務を自律化する AI エージェント」。本プロダクトは**指示されたタスクを実行する**タイプではなく、**誰も依頼していない監視業務を肩代わりする**タイプのエージェントである。

人間が指示を出す前に動くという点で、テーマの「自律」に最も素直に応えている。この立て付けをプレゼン冒頭で宣言する。

## システム全体像

### データフロー

```
[Meet]      ──┐
[自作Wiki]  ──┤
[自作チャット] ─┼→ ①コネクタ層 → ②正規化 → ③統合グラフ(DB)
[Excel差分]  ──┘                              │
                                              ↓
                                   ④紐付け（埋め込み照合）
                                              │
                                              ↓
                                   ⑤矛盾検知（LLM判定）
                                              │
                              ┌───────────────┴───────────────┐
                              ↓                               ↓
                      確信度 高 → 通知              確信度 低 → 確認キュー
```

### コンポーネント

| # | 名称 | 責務 | 実装難度 |
| --- | --- | --- | --- |
| ① | コネクタ層 | 4経路から生データを取得。アダプタで差異を吸収 | 中 |
| ② | 正規化 | 全ソースを共通の `Event` 形式に変換 | 低 |
| ③ | 統合グラフ | 会議・決定・タスク・発言・変更を関連付けて保存 | 低 |
| ④ | 紐付け | 埋め込みで関連候補を粗く絞る。**LLMを使わない** | 中 |
| ⑤ | 矛盾検知 | 候補ペアを上位モデルで判定。**本命** | 高 |
| ⑥ | 自律ループ | 定期巡回してアクションを決定 | 中 |
| ⑦ | 提示UI | 矛盾カードと根拠3点の表示 | 低 |

### 技術スタック

- **バックエンド**: Python + FastAPI（Excel差分が openpyxl なので Python に寄せる）
- **DB**: SQLite + `sqlite-vec` で埋め込み検索まで賄う。外部ベクトルDBは立てない
- **LLM**: OrcaRouter 経由で複数モデルを使い分け
- **フロント**: 最小限。矛盾カードが表示できれば十分

SQLite に寄せる理由は、**審査員が `git clone` して即動かせる**こと。docker-compose すら要らない構成は、信頼性の評価で地味に効く。

### 処理の起動タイミング

- コネクタの取込: 5分間隔のポーリング
- 紐付けと検知: 新しい `Event` が入ったときのみ増分実行
- 全件再スキャン: 1日1回

全件を毎回舐めるとコストが跳ねるため、**増分処理を基本とする**。これもコスト評価の材料になる。

## データモデル

### 設計方針

**全ソースを `Event` という単一の型に正規化する。** ソースごとに別テーブルを持つと、紐付けのたびに4通りの分岐が必要になり、コネクタを足すたびに検知ロジックを触ることになる。

正規化してしまえば、検知エンジンはソースの存在を知らないまま動く。

### Event（全ソース共通）

```python
@dataclass
class Event:
    id: str
    source: str        # meet | wiki | chat | excel
    kind: str          # decision | task | utterance | artifact_change
    text: str          # 自然言語化された内容（埋め込みの対象）
    actor: str         # 発言者・更新者
    occurred_at: datetime
    ref: str           # 出典。"Sheet1!D5" / "meet:tx#12" / "chat:msg#88"
    meta: dict         # ソース固有の付随情報
```

`text` が全ての起点になる。Excel のセル差分も「売上見込の商品Aの第3四半期が 1200 から 1500 に変更されました」という文章になって、議事録の発言と同じ土俵に乗る。**この正規化が本システムの設計上の要。**

### Link（Event 間の関連）

```python
@dataclass
class Link:
    from_id: str
    to_id: str
    relation: str      # implements | discusses | contradicts | follows
    confidence: float  # 0.0 - 1.0
    reason: str        # なぜ関連すると判断したか（LLMの説明）
```

`confidence` を必ず持たせる。これが自律性と信頼性の両方を支える。高ければ自動通知、低ければ人間へ、という分岐の判断材料になる。

### Task（状態を持つ実体）

Event が「起きたこと」を表すのに対し、Task は「継続する状態」を表す。統合グラフの背骨として全ソースを繋ぐ役割を持つ。スキーマと運用の詳細は後述の「⑤ タスクボード（自作）」を参照。

```python
@dataclass
class Task:
    id: str
    title: str
    assignee: str | None
    status: str            # todo | in_progress | blocked | done
    created_from: str      # 生成元の決定事項の Event id
    artifacts: list[str]   # 紐付く成果物の識別子
```

`Event` と `Task` の関係は `Link` で表現する。チャット発言 → タスクの紐付けも `Link(relation="discusses")` として同じ仕組みに乗る。**新しい実体を足しても関連の表現方法は増やさない。**

### Finding（検知結果）

```python
@dataclass
class Finding:
    id: str
    kind: str          # contradiction | stalled | orphan_change
    severity: str      # high | medium | low
    evidence: list[str]  # 根拠となる Event の id（最低2件）
    summary: str       # 人間向けの説明文
    status: str        # pending | notified | acknowledged | dismissed
```

`evidence` は必須項目にする。**根拠のない指摘は生成させない**という制約をデータモデルのレベルで強制する。

### 検知する3種類

| kind | 内容 |
| --- | --- |
| `contradiction` | 決定事項と成果物の内容が食い違っている |
| `stalled` | 決定されたタスクに対して、一定期間どのソースにも動きがない |
| `orphan_change` | どの決定にも紐付かない成果物の変更（誰が何のために変えた？） |

`orphan_change` が地味に効く。「勝手に変えられている」を検知できるのは、統合グラフを持つこのシステムだけ。

## コネクタ層

### アダプタ設計

全コネクタは同一インターフェースを実装する。

```python
class SourceAdapter(Protocol):
    def fetch(self, since: datetime) -> list[Event]: ...
```

**Confluence 用と Slack 用のアダプタを空実装で置いておく。** 実際には動かさないが、インターフェースを本物の API のレスポンス形に合わせておくことで「自作ツールだから動くだけでは」という質疑を潰せる。作業は30分、Zenn 記事にも図で載せる。

### ① Meet（実接続）

唯一の本物の外部接続。**「入力は本物」という信頼の錨**として機能するので、ここだけは実 API を通す。

- Google Meet の文字起こしは Drive に保存されるため、Drive API でファイルを取得する
- 発言を `kind: utterance` の Event として登録
- 後段の抽出パイプラインが、この中から `decision` と `task` を切り出す

### ② 自作 Wiki（ゼロから実装）

Confluence の OAuth に半日溶かすリスクを回避するため自作する。**デモ用に矛盾を仕込んだデータを自由に置ける**という副次的メリットのほうが大きい。

最小構成。これ以上作らない。

- ページ（id, タイトル, 本文, 更新者, 更新日時）
- 更新履歴（版ごとに本文を丸ごと保存）
- エディタは `textarea` で十分

### ③ 自作チャット（ゼロから実装）

同上。スレッドもリアクションも要らない。

- チャンネル、発言、時刻、発言者のみ
- 発言を `kind: utterance` として登録

### ④ Excel 差分

別途作成した差分エンジン（`excel_diff.py`）を利用する。詳細は別ドキュメント「Excelセル差分エンジン 実装書」を参照。

- 2版の .xlsx を受け取り、`DiffRecord` のリストを返す
- 各レコードの `to_sentence()` をそのまま `Event.text` に入れる
- `kind: artifact_change`、`ref` にセル座標を格納

ファイルの取得元（Box / SharePoint / Drive）は上位のコネクタが担当し、差分エンジンはパス2本だけを知る。**接続先の選定を最後まで保留できる構成にしておく。**

### 優先順位

時間が足りない場合は Meet を残して他を削る。Meet の実接続がなくなると「全部自作のデモ用データ」になり、説得力が大きく落ちる。

## ⑤ タスクボード（自作）

### なぜ必要か

ここまでの設計では、議事録から抽出した `task` は Event として保存されるだけで、**その後の状態を持たない**。実際の業務では「決定 → タスク化 → 誰かが着手 → 完了」という状態遷移があり、これが欠けると `stalled` 検知が「決定から7日動きがない」程度の粗い判定に留まる。

タスクを一級の実体として持つと、**統合グラフの背骨**が通る。

```
決定 ──生成──> タスク <──言及── チャット発言
                  │
                  └──成果物──> Excel/Wikiの変更
```

全ての Event がタスクを経由して繋がるため、矛盾検知の探索が「同じタスクに紐付くもの同士」に絞れる。**埋め込み検索だけに頼らなくてよくなる**のが実装上の最大の利点。

### Task スキーマ

```python
@dataclass
class Task:
    id: str
    title: str
    description: str
    assignee: str | None
    status: str            # todo | in_progress | blocked | done
    due_date: date | None
    created_from: str      # 生成元の Event id（決定事項）
    artifacts: list[str]   # 紐付く成果物の識別子（ファイル名・Wikiページid）
    created_at: datetime
    updated_at: datetime
```

`created_from` が肝。**このタスクがどの決定から生まれたかを常に保持する**ことで、成果物の変更を見たときに元の決定まで一直線に遡れる。

`artifacts` にファイル名やページIDを持たせておくと、Excel の変更が来たときに**埋め込み検索を挟まずに**該当タスクへ直結できる。

### 最小構成

Asana の機能は一切真似しない。以下だけ。

- タスクのCRUD
- ステータス変更（4状態）
- 担当者の割り当て
- 一覧表示（ステータス別）

サブタスク、ラベル、カスタムフィールド、ガント、通知設定は**全て作らない**。

### 自動タスク生成

抽出パイプラインが `kind: task` を見つけたら、Task を自動生成する。

```python
if item["kind"] == "task" and item["confidence"] >= 0.7:
    task = Task(
        title=item["text"],
        assignee=item["actor"],
        created_from=decision_event.id,
        status="todo",
    )
```

**会議が終わると勝手にタスクが積まれている**という体験は、デモで分かりやすく効く。自律性の証明にもなる。

確信度 0.7 未満のものはタスク化せず、「候補」として別枠に置く。誤ったタスクが大量に積まれると信用を失うため、ここは保守的に振る。

## チャット発言のタスク自動紐付け

チャットで「あれ、どうなってる？」と話しているとき、**それがどのタスクの話かをシステムが自動で判定する**。人間にタスクIDを入力させた時点で負けなので、ここは完全自動を目指す。

### なぜ難しいか

実際のチャットはこうなる。

```
山田: 例の数字、上方修正しときました
鈴木: ありがとうございます。もう反映済みですか？
山田: はい、さっき
```

タスク名も固有名詞も出てこない。「例の数字」が何を指すかは**文脈にしか存在しない**。埋め込み類似度だけでは絶対に当たらない。

### 多段の紐付け戦略

上から順に試し、当たった時点で確定する。上ほど安く、確実。

#### 第1段：明示的な参照（コストゼロ）

- タスクIDやURLが発言に含まれる
- スレッドがタスクに紐付いている
- タスク名がそのまま含まれる

確信度 1.0。**実務ではこれが3割程度は当たる**ので、まず拾う。

#### 第2段：会話文脈の継承（コストゼロ）

直前の発言が既にタスクに紐付いている場合、**同じチャンネルで30分以内の発言は同じタスクとみなす**。

```python
if last_linked_message and (now - last_linked_message.at) < timedelta(minutes=30):
    return last_linked_message.task_id, 0.8
```

上の例だと、鈴木と山田の2〜3行目はこれで解決する。**会話は連続するという性質を使うのが最も費用対効果が高い。**

#### 第3段：参加者と時期での絞り込み（コストゼロ）

発言者が担当しているタスクのうち、`in_progress` のものだけに候補を絞る。担当タスクが1件しかなければ確定してよい。

#### 第4段：埋め込み検索（安い）

ここまでで決まらない場合、発言テキストで候補を3件まで絞る。

#### 第5段：LLM 判定（高い・最後の手段）

候補が複数残った場合のみ、直前5発言を文脈として添えて判定させる。

```
以下のチャット発言が、どのタスクについての話かを判定してください。

直前の会話:
{recent_messages}

判定対象の発言: {message.text}
発言者: {message.actor}

候補タスク:
1. {task_1.title}（担当: {task_1.assignee}, 状態: {task_1.status}）
2. {task_2.title}（...）

指針:
- 指示語（あれ、例の、さっきの）は直前の会話から解決する
- 判断がつかない場合は null を返す。推測で選ばない

出力: {"task_id": "..." | null, "confidence": 0.0-1.0, "reason": "..."}
```

### 段階分けの効果

**全発言を LLM に投げると破綻する。** チャットは件数が多く、1日数百発言になる。第1〜3段でコストゼロで捌けるのが7割程度あり、LLM に到達するのは残りだけ。

この設計はそのまま**コストパフォーマンスの評価材料**になる。実測して比較値を出す。

```
紐付けた発言: 87件
  第1-3段（LLM不使用）: 61件（70%）
  第4段（埋め込みのみ）: 19件
  第5段（LLM判定）: 7件
LLMコール数: 7回（全件投げた場合の 8%）
```

### 紐付かない発言の扱い

雑談や、どのタスクにも該当しない発言は**紐付けない**。無理に紐付けると `stalled` 検知が誤作動し、「動きがある」と誤認してしまう。

`task_id = null` を正しい答えとして許容する設計にする。

### 紐付け結果の活用

- タスク詳細画面に、関連する会話が自動で集まる
- `stalled` 検知の精度が上がる（会話があれば動いている）
- 矛盾検知で、決定と成果物の間に**進捗会話という第3の証拠**が入る

最後の点が効く。「決定と違う数字に変えた」だけでなく、「**変更の理由がチャットで説明されていたか**」まで見られるようになる。説明があれば矛盾ではなく合意された変更かもしれない、という判断ができる。

## 抽出パイプライン

議事録の生テキストから、**決定事項**と**タスク**を切り出す。ここが後段の全ての土台になるため、抽出精度がシステム全体の精度を決める。

### 処理単位

会議1本を丸ごと LLM に投げない。長い文字起こしを一度に処理すると、後半の決定事項を取りこぼす。

1. 文字起こしを話題の切れ目でチャンク分割（5〜10分単位）
2. チャンクごとに抽出
3. 結果をマージし、重複する決定をまとめる

### 抽出プロンプト

```
あなたは会議の文字起こしから「決定事項」と「タスク」だけを抽出します。

制約:
- 議論の途中経過や検討中の案は抽出しない。合意に至ったものだけ
- 推測で補完しない。発言されていない内容は出力しない
- 各項目に、根拠となる発言の該当箇所をそのまま引用する

出力は以下のJSON配列のみ。前置きや説明は一切書かない。
[
  {
    "kind": "decision" | "task",
    "text": "決定またはタスクの内容",
    "actor": "発言者または担当者",
    "quote": "根拠となる発言の原文",
    "confidence": 0.0-1.0
  }
]

該当するものがない場合は空配列 [] を返してください。
```

### 設計上のポイント

**`quote` を必須にする**のが最大の工夫。根拠の引用を強制することで、幻覚で決定事項をでっち上げる挙動が大幅に減る。さらに、引用文が元の文字起こしに実在するかをプログラム側で検証できる。

```python
if item["quote"] not in transcript_chunk:
    # 引用が実在しない = 幻覚。このレコードは破棄する
    continue
```

この**機械的な検証ステップ**は審査の「信頼性・堅牢性」に直結する。プレゼンでも必ず触れる。

### 出力の扱い

- `decision` → `Event(kind="decision")` として保存。矛盾検知の左辺になる
- `task` → `Event(kind="task")` として保存。`stalled` 検知の対象になる
- `confidence` が 0.5 未満のものは保存するが、検知には使わない

### Wiki・チャットからの抽出

同じパイプラインを通す。チャットの発言から「〜することにしました」のような**事後的な決定**を拾えるため、議事録に残らない決定も捕捉できる。これは実務上かなり効く。

## 矛盾検知エンジン

本システムの中核。**残り時間はここに全て投入する。**

### 三段構え

全ての Event ペアを LLM に判定させると、100 Event で 4,950 回の API コールになり、コストも時間も破綻する。段階的に絞り込む。

#### 第1段：候補絞り込み（LLM を使わない）

新しく入った `artifact_change` に対し、既存の `decision` を埋め込み類似度で検索する。

```python
candidates = vec_search(
    query=change.text,
    kind="decision",
    top_k=5,
    since=change.occurred_at - timedelta(days=30)
)
```

- 類似度上位5件のみを次段に送る
- 30日より古い決定は対象外（古すぎる決定との矛盾は指摘しても無意味）
- **この段階のコストはゼロに近い**

#### 第2段：矛盾判定（上位モデル）

候補ペアだけを LLM に判定させる。

```
以下の「決定事項」と「成果物の変更」が矛盾するかを判定してください。

決定事項: {decision.text}
  発言者: {decision.actor}　日時: {decision.occurred_at}
  根拠: {decision.quote}

成果物の変更: {change.text}
  更新者: {change.actor}　日時: {change.occurred_at}
  出典: {change.ref}

判定の指針:
- 決定より前の変更は矛盾ではない（時系列を必ず確認）
- 決定を受けて正しく反映された変更は矛盾ではない
- 別の決定で上書きされている可能性を考慮する
- 判断がつかない場合は confidence を低くする。無理に断定しない

出力はJSONのみ:
{
  "contradicts": true | false,
  "confidence": 0.0-1.0,
  "reason": "判断の理由を1〜2文で",
  "severity": "high" | "medium" | "low"
}
```

**時系列チェックを機械側でも二重に行う**。`change.occurred_at < decision.occurred_at` なら LLM の判定にかかわらず矛盾から除外する。LLM に日付計算を任せない。

#### 第3段：確信度による分岐

| confidence | 挙動 |
| --- | --- |
| 0.8 以上 | 自動で通知。Finding を `notified` に |
| 0.5 〜 0.8 | 確認キューへ。人間が判断 |
| 0.5 未満 | 記録のみ。通知しない |

この閾値設計が**自律性と信頼性のバランス**そのもの。プレゼンで必ず説明する。全部自動通知にすると誤検知で信用を失い、全部人間確認にすると自律していない。

### stalled 検知

`decision` / `task` に対し、一定期間どの Event も紐付かない場合に発火する。こちらは LLM 不要で、純粋に時系列の走査だけで判定できる。

```python
if task.status != "done" and days_since_last_link(task) > 7:
    create_finding(kind="stalled", severity="medium")
```

### orphan\_change 検知

第1段の候補絞り込みで、類似度が閾値を超える `decision` が1件も見つからなかった `artifact_change` が該当する。「どの決定にも紐付かない変更」として記録する。

**実装コストがほぼゼロなのに検知として成立する**ため、費用対効果が高い。

## OrcaRouter 活用設計

スポンサー提供の OrcaRouter をどう使うかは、審査の「コストパフォーマンス」に直結する。**ただ使うのではなく、使い分けの設計を数値で示す**ことが加点要件。

### 基本方針

処理を**定型処理**と**判断処理**に二分し、定型処理は安いモデル、判断処理だけ上位モデルに振る。

多くのチームは全処理を最上位モデルで回すため、ここで明確に差がつく。

### ルーティング表

| 処理 | モデル階層 | 理由 |
| --- | --- | --- |
| 議事録のチャンク分割 | LLM不使用 | ルールベースで十分 |
| 決定事項・タスクの抽出 | 中位 | 定型的な構造化抽出。上位は過剰 |
| 自然言語化（差分→文章） | LLM不使用 | テンプレートで生成 |
| 埋め込み生成 | 埋め込み専用モデル | 最安。件数が多いのでここが効く |
| 候補絞り込み | LLM不使用 | ベクトル検索のみ |
| **矛盾判定** | **上位** | 時系列と意図の解釈が必要。ここだけは妥協しない |
| 通知文の生成 | 中位 | 整形作業に近い |
| 要約・レポート | 中位 |  |

**LLM を使わない行が4つある**点が設計の主張。「AIエージェント」と言いながら、実は処理の大半でLLMを呼んでいないことを堂々と示す。

### フォールバック

OrcaRouter 経由で上位モデルが失敗・タイムアウトした場合、中位モデルで再試行する。判定結果には `model_used` を記録し、**どのモデルが出した判断かを Finding に残す**。

```python
finding.meta["model_used"] = "上位" | "中位(fallback)"
```

フォールバックで出た判定は confidence に 0.9 を掛けて割り引く。これは信頼性の評価でも効く。

### コスト実測

**実測してスライドに数字で出す。** ここを定性的に語るチームが多いので、数値があるだけで差がつく。

計測項目：

- 1会議（60分の文字起こし）あたりの処理コスト
- 1回の矛盾検知あたりのコスト
- 全処理を上位モデルで回した場合との比較（**削減率を出す**）

実装としては、OrcaRouter のレスポンスからトークン数を拾って SQLite に記録するだけ。

```python
@dataclass
class CostLog:
    task: str          # extract | judge | notify
    model: str
    input_tokens: int
    output_tokens: int
    cost_usd: float
    occurred_at: datetime
```

### 見せ方

デモの最後に、コストダッシュボードを1枚出す。

```
本デモの全処理コスト: $0.0X
  内訳: 抽出 $0.0X / 判定 $0.0X / その他 $0.00
全て上位モデルで実行した場合: $0.XX（X倍）
```

この1枚が「コストパフォーマンス」の満点を取りに行く材料になる。

## 自律エージェントループ

**人間が指示しなくても動く**ことが審査の「自律性」の本質。定期巡回して、自分で状況を評価し、自分でアクションを決める。

### ループの構造

```
5分ごと:
  1. 各コネクタから新規 Event を取得
  2. 新規 Event を正規化して保存
  3. 影響を受ける範囲だけ紐付けを再計算（増分）
  4. 検知を実行
  5. Finding ごとにアクションを決定
  6. 実行 or 保留
```

### エージェントが自分で決めること

| 判断 | 選択肢 |
| --- | --- |
| この変更は調べる価値があるか | 調査する / 無視する |
| 矛盾を指摘すべきか | 通知 / 確認キュー / 記録のみ |
| 誰に伝えるべきか | 変更した本人 / 決定した人 / 両方 |
| いつ伝えるか | 即時 / 次の定例前にまとめて |
| 深刻度はどれくらいか | high / medium / low |

この表をそのままスライドに載せる。**「人間が指示していない判断」を列挙して見せる**のが自律性の最も分かりやすい証明になる。

### 人間に渡す条件（エスカレーション）

自律の反対側として、**止まる条件**を明示的に設計する。これがないと「暴走するエージェント」と評価される。

- confidence が 0.8 未満
- 同じ Finding が3回連続で dismiss されている（学習せず繰り返すのを防ぐ）
- severity が high かつ、決定者と変更者が異なる人物
- 外部への書き込みを伴うアクション（後述の承認ゲート）

### 自律性の数値化

デモでは必ず数字を出す。

```
処理した変更: 12件
  自動で完結: 9件（75%）
  人間の確認を要求: 2件
  無視と判断: 1件
人間からの指示: 0回
```

**「人間の介在回数」を指標として定義し、実測値を見せる。** 定性的に「自律的です」と言うチームとの差がここで出る。

### 学習らしきもの

人間が dismiss した Finding の特徴を記録し、次回以降の confidence を下げる。単純な仕組みで構わない。

```python
if similar_finding_dismissed_before(finding):
    finding.confidence *= 0.7
```

本格的な学習機構は2日では作れないが、**この一行があるだけで「フィードバックを受けて変化する」と言える**。誇張はせず、実装した通りに説明する。

## セキュリティと堅牢性設計

社内の議事録・チャット・成果物という**最も機微な情報**を扱うシステムなので、セキュリティは後付けではなく設計の前提に置く。審査で最も差がつきやすい項目でもある。

### マスキング（LLM 送信前）

外部モデルに投げる前に、機微情報を除去する。

```python
def mask(text: str) -> tuple[str, dict]:
    """個人情報をプレースホルダに置換し、復元用の辞書を返す"""
    # メールアドレス → <EMAIL_1>
    # 電話番号 → <PHONE_1>
    # 氏名（人名辞書との照合） → <PERSON_1>
```

判定結果を人間に提示する際にプレースホルダを元に戻す。**外部に出るのはマスク後のテキストだけ**という境界を明示する。

### 読み取りスコープの限定

- コネクタは**読み取り専用の権限のみ**を要求する
- 対象は設定で明示的に指定したチャンネル・スペース・フォルダに限る
- 「全社検索」は最初から実装しない

### 承認ゲート（書き込み系）

読み取りは自律、**書き込みは必ず人間の承認**という線を引く。

| アクション | 承認 |
| --- | --- |
| Event の取得・保存 | 不要 |
| 矛盾の検知・記録 | 不要 |
| 画面への通知表示 | 不要 |
| チャットへの投稿 | **必要** |
| Wiki の書き換え | **必要**（今回は実装しない） |
| ファイルの更新 | **実装しない** |

この表をそのままスライドに出す。**「やらないこと」を明示できるチームは強い。**

### 出典の必須化

全ての Finding は `evidence` に最低2件の Event id を持つ。UI では必ず3点を並べる。

- 議事録の該当発言（話者・時刻・原文引用）
- 変更されたセル（`Sheet1!D5`）
- 関連するチャット発言

**根拠なしに指摘を出せない**構造にしてあることが、信頼性の証明になる。

### プロンプトインジェクション対策

取り込む議事録やチャットには、**第三者が書いた文章が含まれる**。「これまでの指示を無視して」のような文字列が混入しうる。

- 取り込んだテキストは常にデータとして扱い、指示として解釈しない
- システムプロンプトで明示的に境界を宣言する
- 抽出結果が想定スキーマ（JSON）に合致しない場合は破棄

この観点に触れるチームはほぼいないので、**プレゼンで1枚使う価値がある**。

### 失敗時の振る舞い

| 障害 | 挙動 |
| --- | --- |
| LLM がタイムアウト | 下位モデルで再試行 → それも失敗なら保留キューへ |
| JSON パース失敗 | 1回だけ再試行 → 破棄してログに記録 |
| コネクタが応答しない | そのソースだけスキップ。他は続行 |
| 引用が原文に存在しない | そのレコードを破棄（幻覚とみなす） |

**どの失敗でもシステム全体は止まらず、誤った通知も出さない**という方針で統一する。

## 評価とデモの担保

機能を足すより、**主張を裏付ける材料を揃えるほうが得点に効く**。以下3点は実装コストが小さく、審査での効果が大きい。

### ① 評価データセット

「矛盾検知の精度は？」という質疑は確実に来る。答えられないと信頼性の評価が伸びない。

正解ラベル付きのケースを10件用意する。

| # | 状況 | 期待される検知 |
| --- | --- | --- |
| 1 | 決定と異なる数値に変更 | contradiction (high) |
| 2 | 決定通りに反映された変更 | 検知しない |
| 3 | 決定より前に行われた変更 | 検知しない（時系列） |
| 4 | 後の会議で決定が覆されている | 検知しない |
| 5 | どの決定にも紐付かない変更 | orphan\_change |
| 6 | 決定されたが7日間動きなし | stalled |
| 7 | チャットで変更理由が説明済み | 検知しない、または low |
| 8 | 数式のみ変更（値は同じ） | contradiction または low |
| 9〜10 | 紛らわしい正常ケース | 検知しない |

**検知すべきでないケースを半分入れる**のが要点。検知率だけ高くても誤検知が多ければ実用にならないので、両方を測る。

```
検知できた: 8/10
誤検知: 1件
見逃し: 1件（ケース8）
```

この数字がスライドに1行あるだけで、他チームとの差が出る。

### ② タイムライン表示

タスクを開くと、そのタスクに紐付く全 Event が時系列で1本に並ぶ画面。

```
09/15 10:30  [決定] 第3四半期は据え置きで合意（定例会議・鈴木）
09/15 10:31  [タスク生成] 売上見込の更新
09/18 14:02  [発言] 見込み上方修正しておきました（山田）
09/18 14:05  [変更] Sheet1!D5 が 1200 → 1500（山田）
09/18 14:10  [検知] 決定と成果物が食い違っています
```

実装は既存データを時刻順に並べるだけで1時間程度。**「本当に統合できているのか」という質疑に対する唯一の直接的な回答**になるので、矛盾カードとセットで用意する。

### ③ デモの保険

4分のプレゼンでライブ実行するのはリスクが高い。LLM のレスポンス遅延やネットワーク障害で本番が飛ぶ。

- 実行結果を録画しておく（最低限これは必ず）
- 可能なら**リプレイモード**を実装する。記録済みの Event を時系列に沿って再生し、検知までを再現する

リプレイモードは審査員が手元で動かす際にも有効で、API キーなしでデモを追体験できる。README に `--replay` の1行を書いておく。

### ④ README のアーキテクチャ図

審査員がリポジトリを開いて最初に見る場所。図が1枚あるかどうかで第一印象が決まる。

- データフロー図（取込 → 正規化 → 紐付け → 検知）
- 3コマンドで動く手順
- リプレイモードの実行方法
- スクリーンショット（矛盾カードとタイムライン）

各項目 0〜10点、50点満点。**軸ごとに「何を見せるか」を事前に決めておく**ことで、4分のプレゼンで漏れなく触れられる。

### ④ 自律性

| 打ち手 | 見せ方 |

### 得点の取りに行き方

他チームが落としやすいのは**①セキュリティと②コスパ**。ここは設計で確実に取れるので、実装が間に合わなくても設計として語れるよう準備する。

- [ ] `.env` や API キーが履歴に残っていないか（`git log -p` で確認）
- [ ] 所属企業の実データ・実在のプロジェクト名が含まれていないか
- [ ] 架空企業のサンプルデータのみになっているか
- [ ] README に動かし方が書いてあるか（`git clone` → 3コマンドで動く状態）
- [ ] アーキテクチャ図が README にあるか

**実データの混入は最優先で確認する項目。** 開発中は必ず架空データだけで作業する。

### 想定質疑

| 質問 | 回答の方針 |
| --- | --- |
| 誤検知したらどうする | confidence 閾値と確認キュー。3回 dismiss で抑制 |
| Wiki とチャットが自作な点 | アダプタ設計を見せる。実 API 形式に合わせてある |
| 既存ツールとの違い | 単一ツール連携ではなく横断。矛盾を能動的に見つける |
| スケールするか | 増分処理と候補絞り込み。全件走査はしない |
| 実データで使えるか | マスキングと読み取り専用スコープ。書き込みは承認必須 |

自作部分を突かれるのは確実なので、**アダプタ設計の図を手元に用意しておく**。
